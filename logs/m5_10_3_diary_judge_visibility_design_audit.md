## 1. Diary Runtime Trace

### 1.1 Storage

```
data/soul/{agent_id}/diary/YYYY-MM-DD.jsonl
  — one file per agent per day
  — one JSON line per entry
```

### 1.2 Entry schema

```json
{
  "ts": "2026-08-11T07:30:00.000000+00:00",   // UTC ISO timestamp
  "slot": "morning",                            // "morning" | "night"
  "content": "角色用日文寫的 1-2 句自我記錄（最多 80 字）",
  "source": "llm",                               // "llm" | "placeholder"
  "inner_life_event_id": "abc123..."              // optional (M5.4-5.3)
}
```

**Content characteristics:**
- Max 80 characters (per `DIARY_MAX_CLEAN_CHARS = 80`)
- Generated by LLM in character's voice (Japanese, persona-driven)
- `generate_diary_entry` uses persona + latest 5 v1 memory facts as context
- Think blocks stripped before writing (`_strip_think`)
- `source="placeholder"` when LLM fails: "（{date} 早上）起牀了。窗外還沒什麼聲音。" / "（{date} 晚上）今天過完了。"

### 1.3 Diary generation pipeline

```
Scheduler fires morning/night trigger
  → DiaryHandler.handle_event (Agency 4 stages)
  → diary_writer_executor(agent_id, slot)
    → diary_callback_factory(agent_id)
      → generate_diary_entry(
          agent_id, slot,
          persona_prompt=personas/{agent_id}.md[:500],
          recent_memories=v1 mirror latest 5 facts,
          inner_life_event_id=canonical event_id
        )
        → LLM call (minimax M2.7)
        → write_entry(agent_id, slot, clean_content, source="llm")
```

**Key design note (diary.py:7-10):**
> "diary 內容 90% 跟 Bry 無關, 角色自己過日子"
> "殘留感: diary 寫進 history, 後續對話角色會引用"

### 1.4 Diary → Judge path

The Judge is called by `MemoryWriter._extract_facts_llm` for every `AGENT_SPEAK` turn. The question is: should the Judge additionally see diary entries when evaluating fact extraction?

### 1.5 What Diary is architecturally (Bry design intent)

From diary.py docstring (lines 4-11):
- **Diary = character's self-awareness** — "diary 是「Bry 從來沒上線過, 角色世界也活」的最直接證據"
- **Subjective narrative** — 90% independent of Bry's presence
- **Character voice** — written in character's persona
- **Emotional reflection** — not factual record
- **Legacy for future conversations** — "diary 寫進 history, 後續對話角色會引用"

## 2. Canonical Diary Reader API

| Method | Signature | Returns |
|---|---|---|
| `DiaryWriter.read_entries(agent_id, date_str)` | `(str, str) → List[Dict]` | All entries for one day |
| `DiaryWriter.recent_entries(agent_id, days=1)` | `(str, int) → List[Dict]` | All entries for last N days |
| `get_diary_writer()` | `() → DiaryWriter` | Singleton factory |

**Canonical source:** `get_diary_writer()` singleton → `DiaryWriter` instance

**Existing production consumers of read_entries:** NONE found in `src/`. The only callers are in `tests/` (audit/test fixtures).

**Key API limitation:**
- `read_entries(agent_id, date_str)` takes a **single date string** (YYYY-MM-DD)
- The Judge runs for **every conversation turn** (potentially multiple turns per day)
- To get "recent diary" you'd need `recent_entries(agent_id, days=N)` with N=1 or more
- Both return raw dict list (no summary field)

**`source` field available:**
- `"llm"`: genuine character self-reflection (high quality)
- `"placeholder"`: generic template when LLM fails (low quality)

## 4. Privacy Assessment

### 4.1 What Diary content is

- **Character's internal monologue** — personal, emotional, self-reflective
- **Not conversation content** — diary is NOT what Bry said in conversation
- **Privacy from whose perspective:**
  - From Bry's perspective: diary entries are the character's private thoughts (not Bry's private data)
  - From character's perspective: diary is the character's self-expression
- **LLM is the same service** that runs the character — no third-party privacy issue

### 4.2 Privacy comparison

| Source | Content type | Privacy sensitivity |
|---|---|---|
| Conversation text | Bry's messages + character responses | HIGH (actual conversation) |
| v1 memory facts | Extracted structured facts | MEDIUM (fact-graph is system data) |
| Diary content | Character's subjective self-reflection | MEDIUM-LOW (character's own voice) |
| Placeholder | Generic template | NONE |

### 4.3 Access control

- Diary entries have **no `source_pair` label** (unlike v1 memory facts)
- Diary is not tied to a specific user-agent conversation pair
- Diary is the character's OWN record, not a conversation transcript

### 4.4 Privacy conclusion

**Diary privacy surface for Judge is not the primary concern.** The more important question is whether diary content helps or hurts Judge quality.

## 5. v1 Memory Overlap Analysis

### 5.1 v1 Memory → Diary (existing, per design)

From `generate_diary_entry` (diary.py line 318-333):
```
LLM prompt uses: recent_memories = v1 mirror latest 5 facts
System prompt: character identity + instruction to write self-reflection
```

**v1 memory shapes what the diary contains.**

### 5.2 Diary → v1 Memory (proposed)

If Judge sees diary content as context for fact extraction:
- Diary entries were generated FROM v1 memory context
- Judge already sees v1 memory context (M5.10-2)
- Diary is derived FROM v1 memory, not additional raw data
- **Significant semantic overlap** between v1 memory context and diary content

### 5.3 Circular dependency risk

```
v1 memory (facts) → diary generation (LLM uses v1 as context)
diary content → Judge context (proposed)
Judge context → fact extraction (evaluates what to remember)
fact extraction → v1 memory (writes new facts)
```

The Judge sees:
1. `text` (current conversation)
2. `v1 memory summary` (what was already remembered)
3. `diary content` (character's reflection on recent experiences, which was itself derived from v1 memory)

**The diary adds no genuinely new information at the fact-extraction level.**

### 5.4 Semantic difference

| v1 Memory | Diary |
|---|---|
| **Objective facts** — what happened | **Subjective self-interpretation** — how the character feels about what happened |
| `("Bry", "likes", "義大利麵")` | "今天吃了很好吃的義大利麵，好幸福。" |
| Structured, graph-based | Free-form character voice |
| LLM-judged (M5.10-2) | LLM-generated (diary pipeline) |

## 6. Core Architectural Question

**"Does Diary provide information that materially improves memory judgment?"**

### 6.1 What Judge evaluates

Given:
- `text`: the raw conversation content
- `context`: additional information (currently v1 memory summary)

The Judge's job is to extract `(subject, predicate, object)` triples and evaluate whether they are SUPPORTED / WEAK / UNSUPPORTED.

### 6.2 Does diary help this job?

**No, for three reasons:**

**R1 — Diary is not evidence, it's interpretation.**
The Judge needs to know: "Did the user actually say/do X?" Diary says: "The character feels Y about X." These are different types of information. The character feeling sad about an event doesn't make the event more or less "true" as a memory fact.

**R2 — Judge already sees the source text.**
The Judge's `text` parameter contains the full conversation. Adding diary context (which is derived from past conversations) doesn't give the Judge new evidence about the current text.

**R3 — Significant overlap with v1 memory.**
Diary was generated using v1 memory as context. The Judge now sees v1 memory. The marginal information from diary, beyond what v1 memory already provides, is minimal.

### 6.3 Counterargument: Diary provides character nuance

Some might argue that diary helps the Judge understand the character's emotional state, which could help with "self_directed" vs "other_directed" stance classification.

**Counter-counterargument:**
- The Judge already evaluates stance via `judge_stance` with `context=""` (empty) — stance classification was working before M5.10-2
- Stance classification is about whether the statement is self-directed (character talking about self) or other-directed — diary doesn't add evidence for this
- The `diary` category in the Judge is about whether a statement is a "personal reflection" — this is determined by the text itself, not by the character's other reflections

## 14. Recommended Decision

### Recommendation: **Option A — No Diary Visibility (Bry Decision: Accept)**

**Rationale:**

1. **Architectural purpose mismatch:** Diary is the character's subjective self-interpretation; Judge evaluates objective fact extraction. These are fundamentally different information types.

2. **No material quality improvement:** v1 memory (now visible to Judge via M5.10-2) already provides the relevant context. Diary content was derived from v1 memory; adding it back doesn't introduce genuinely new evidence.

3. **Quality > Quantity:** More context isn't automatically better. The Judge already struggles with empty context. Adding subjective character narrative (max 80 chars, persona voice) could introduce LLM bias rather than improve accuracy.

4. **No frozen contract violation needed:** The implementation would be trivial (add `DiaryWriter` to `MemoryWriter.__init__`, call `read_entries`). The reason to reject is not technical difficulty but architectural appropriateness.

5. **"No Memory > Wrong Memory" principle:** If diary context could lead the Judge to extract facts that are supported by the character's emotional interpretation but not by the actual text, that's "Wrong Memory."

### Architectural principle this reinforces:

**v1 Memory = objective fact record (for Judge)**
**Diary = subjective character self-awareness (for character continuity / future conversations)**
**These are separate systems for separate purposes. Do not conflate them.**

## 17. Summary

M5.10-3 is a **design audit with clear conclusion**: Diary content should NOT be visible to the Memory LLM Judge. This is not a technical limitation but an architectural design choice — Diary serves a fundamentally different purpose (character self-awareness / subjective narrative) from what the Judge needs (objective factual evidence from source text). The Diary was generated from v1 memory context; the Judge now sees v1 memory; adding diary adds no genuinely new information while potentially introducing persona bias into fact extraction.

**Decision: Accept Option A. M5.10-3 CLOSED. No code change required.**
