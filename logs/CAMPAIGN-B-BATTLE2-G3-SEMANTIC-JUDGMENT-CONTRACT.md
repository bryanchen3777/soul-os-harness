## 二、甲與乙的**架構差異**（主大腦釐清，避免實作時混淆）

兩條路線**都**用「同候選維度」做**結構預濾**；**差別在「誰做最後裁決」**：

| | 路線乙（否決） | 路線甲（採納） |
|---|---|---|
| 結構預濾 | 同維度 ＋ 跨日 ＋ 內容不同 | 同維度 ＋ 跨日 ＋ 內容不同（**相同**） |
| **最後裁決** | **結構預濾＝矛盾判定**（直接視為矛盾） | **真實 LLM 語意判定**（輸出 `CONTRADICT`／`COMPATIBLE`） |
| 「今天下雨很冷」→「今天出太陽很暖」 | 會被**誤判為矛盾** ⇒ 誤殺命題 | 預濾命中、但語意判定回 `COMPATIBLE` ⇒ **不記錄矛盾** |

⇒ **一句話**：甲把結構預濾降格為「**值得問一句**」的門檻，**最後裁決交給語意判斷**；
乙則把預濾**升格**成裁決本身。**實作時這兩者只差「最後一步誰說了算」。**

## 三、預算防禦上限（Owner 核定，**逐條硬性**）

| 項 | 上限 | 備註 |
|---|---|---|
| **觸發頻率** | **非常態**：僅在「既有節點與新生成候選命題之間發生**顯式衝突嫌疑**」時方得觸發 | 不是每晚掃描 |

### 三之二、🔺 「300 Tokens」作為**成本上界**的誠實界定（既有實測事實）

Owner 裁定「單次上限 300 Tokens」——**這條要成立，必須區分「請求值」與「上界」**。
主大腦查到 canonical 內 2026-10-24 的付費校準（`b7cdcf3`，1 次，`deepseek-v4.1-flash`）已記錄：

> prompt 121 ＋ completion **1790** ＝ 1911 tokens、延遲 **26.34 s**、`finish_reason=stop`、回應為合法 JSON
> ⇒ (a) **`max_completion_tokens=300` 不被 provider 遵守**（實際約 6 倍，其中 ~1690 為**推理 token 且照樣計費**）
> ⇒ **300 不是成本上界**；(b) 26.34 s > 當時的 20 s 逾時 ⇒ 照原值接線會「**錢已花掉、結果被丟棄**」

**三條現況核對（2026-10-24 18:0x EDT）**：

| # | 現況 | 證據 | 對本契約的影響 |
|---|---|---|---|
| 1 | 代理的 HTTP 逾時**已是 120 s** | `src/llm/proxy.py:2095,2314` `httpx.AsyncClient(timeout=120.0)` | ✅ 26.34 s 級延遲**不會**被丟棄 ⇒ 「錢花掉、結果丟棄」的危險**已解除**；判定呼叫的逾時**必須**走既有代理層（不得另設更短逾時） |
| 2 | `max_tokens` 是**config 來的可覆寫值** | `configs/loader.py:199` `max_tokens=llm_cfg.get("max_tokens", 300)` | ⇒ 「≤300」**必須由呼叫端顯式傳入**（與 P5-② 的 `max_tokens=400` 同一套路），**不得**依賴 config 預設值（可被覆寫） |
| 3 | provider **不遵守** token 上限 | 上引校準實測（1790 vs 300） | ⇒ 「300」**只能是語意上界**（不採用超額輸出），**不能**宣稱是帳務上界 |

⇒ **誠實的預算上界陳述**：
- **唯一硬的帳務上界 ＝ 呼叫次數**（每 Agent 每日 ≤1 次 ⇒ 每日 ≤ 1 次實際付費呼叫）。
- **token 數只能做成語意上界**：取得回應後若 usage 的 completion tokens **> 上限**
  ⇒ **視為超額 ⇒ 該輸出不採用（fail-closed）**。⚠️ 注意：此時**帳務已發生**，
  所以這條護欄**降低的是「錯誤輸出被採用」的風險，不是帳務成本**。
- ⇒ G-3 工單**必須**寫死：① 逾時走既有代理層（120 s）；② `max_tokens` 由呼叫端**顯式**傳；
  ③ 回應超額 ⇒ 不採用且 fail-closed；④ **不得**在文件或回報中把 300 稱為「成本上界」。

### 🔺 Fail-Closed 的**方向**（本片最關鍵的一條）

不可判定（預算用盡／例外／空回應／解析失敗／超時）⇒ **視為 `COMPATIBLE`**
⇒ **不寫入任何矛盾紀錄** ⇒ **寧可漏記矛盾，不可誤記矛盾**。

⇒ 這與「Fail-Closed＝保守不動作」的一般語意一致，且方向正確：
**漏記**只是讓召回池少一顆命題；**誤記**會讓一個活著的命題被誤殺（不可逆）。

## 四、機制鏈（F2／F3 已實測釘死）

```
【日 1】某 soul node 收到「顯式衝突嫌疑」的候選命題
        └─ 結構預濾命中（同一候選維度 ＋ 跨日 ＋ 內容不同）⇒ 值得問一句
        └─ 語意判定：每 agent 每日 1 次、≤300 tokens、retries=0、二元輸出、fail-closed
        └─ 判定 = CONTRADICT ⇒ 呼叫 engine.record_contradiction(node_id, source_id=<新 source>,
                                        event_identity=<該日專屬>, ts=<該日>)
                    ⚠️ 必須**每天不同的 source_id**（F3：`(source_id, event_identity)` 冪等去重，
                       同一 source_id 跨日重呼會被吃掉 ⇒ spread 永遠停在 1 天）
        └─ 判定 = COMPATIBLE / 不可判定 ⇒ **不記錄**（不製造假矛盾）

【日 2】再有一天出現同樣的衝突嫌疑（新的 source_id）
        └─ record_contradiction（不同 source_id、不同 ts）⇒ spread = 2

【日 3】第三天（同上）
        └─ record_contradiction（不同 source_id、不同 ts）⇒ independent = 3、spread = 3
        └─ 呼叫 engine.supersede(node_id, source_ids=[該日 source], ...) ⇒
           🔺 supersede() 內部會**先**把 source_ids 寫進累積器、**再**判定門檻
              ⇒ 第 3 次呼叫時 independent ≥ LIFECYCLE_N_SUPERSEDE(3) 且 spread ≥ 2
              ⇒ **成功**：新節點（同層、parent=舊、depth=舊+1）、舊節點 → SUPERSEDED（凍結保留）
        └─ ⇒ 召回池第一次有**合規**命題（`superseded` 節點）
```

🔺 **`supersede()` 的門檻一個字都不動**：`LIFECYCLE_N_SUPERSEDE=3`／
`LIFECYCLE_SUPERSEDE_MIN_DAYS_SPREAD=2`／`LIFECYCLE_ESSENCE_N_SUPERSEDE=5`／
`LIFECYCLE_ESSENCE_CONFIDENCE_DELTA=0.3`（外部套件，repo 外，**不可改**）。

## 五、與 G-1／G-2 的關係（**修正 §0.1.72 的措辭**）

- **機械上獨立**：`engine.supersede()` 對 **depth-1** 節點即可（門檻只看矛盾數／跨日／essence 額外條件）

  而**舊證據血統正是 G-2 預置進 `provenance` 的 `old_source_ids`**
  ⇒ **G-1＋G-2 是 G-3 的合理前置**（先有真血統，再問「這條血統上的新命題是不是互斥」）。
- ⇒ 切片順序維持：**G-1＋G-2 → G-3**。
